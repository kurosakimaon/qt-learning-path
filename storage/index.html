💾 第捌阶段 · 数据与持久化

「这份数据归谁、以什么形状落盘、下次怎么原样拿回来」 · 6 章从配置到数据库

📖 模块简介

前七个阶段，你的程序一关掉，什么都留不下。这一阶段解决「活过进程重启」：用户上次把窗口拖到哪儿、上次输入了什么、 列表里那一千条记录、图标和样式表这些不该让用户改坏的资源——它们各自该住在一个什么形状的容器里。

持久化最容易学歪的地方，是把它当成「调几个 API 存一下」。真正会咬人的是四件跟 API 无关的事： 时机（什么时候写、什么时候读、什么时候 flush）、类型（存进去的是 `42` 还是 `"42"`）、 失败（磁盘满了、文件被占用、JSON 写歪了，你怎么知道）、完整性（写到一半掉电，文件会不会变成半截）。 本模块每一讲都从这四件事出发，而不是从类名出发。

本模块共 6 章：第 1 讲 QSettings（最小的一块持久化，坑全在时机与类型）； 第 2 讲文件与 IO 设备（QFile / QTextStream / QSaveFile / QLockFile / QDir）； 第 3 讲 JSON（它看着像 Map，其实是 CBOR 容器上的一层薄皮）；第 4 讲资源系统（把图标、qss、翻译编进 exe）； 第 5 讲 Qt SQL（连接名、绑定值、事务、错误四件事）；第 6 讲把数据库接上界面（模型是缓存、视图是投影、中间还隔着代理）。 所有示例都不碰你的真实用户目录：QSettings 用 setPath 改道到临时目录，数据库用 :memory:， 临时文件用完就删。跑完自己吐结论，不需要你动手点。

环境事实：Qt 6.12.0、Windows、MinGW-w64 GCC 13.1.0（Qt 官方安装器自带：D:\Qt\Tools\mingw1310_64）、CMake ≥ 3.21（本机 3.30.5）+ 生成器 MinGW Makefiles、C++17。 目标名 storage_01_qsettings … storage_06_sql_model_view，已在顶层 CMakeLists.txt 的 「第捌阶段 · 数据与持久化（storage/）」一节登记；本组额外链 Qt6::Sql 与 Qt6::Xml， 第 4 讲的 resource_demo.qrc 由 AUTORCC 处理。

实测口径：本模块 6 个目标已在本机真实编译、链接、运行（Qt 6.12.0 + MinGW 13.1.0， Windows，QT_QPA_PLATFORM=offscreen），包含在顶层 ctest 的 73/73 里； 硬账条数各讲自己报：第 1 讲 56/56、第 3 讲 对不上 0 行 → exit(0)、 第 5 讲 77/77（含「QSQLITE 驱动插件可用」这一发）、第 6 讲 退出码 0。 每个 .cpp 也过 moc + g++ -std=c++17 -Wall -Wextra（零 error、零 warning）， 类、函数、枚举值都对着 D:\Qt\6.12.0\mingw_64\include 逐字核对过。 ★ 原来标成 Soft 的那几条，凡是运行期能问出答案的都已经问出来了： 「重新查询丢不丢未提交的改动」实测是丢——setFilter 之后 isDirty 直接清零、那一行回到库里的旧值；setEditStrategy() 进门先 revertAll() 也是同一记闷棍。所以规矩照旧要写死：任何触发重新查询的动作前面 都得先 submitAll() 或给一个明确的「放弃修改」确认框。 原始输出存档在 runlogs/<目标名>.log（重跑：bash _tools/run_all.sh '^storage'）。

📂 学习文件列表

6 张卡片 = 6 章，按 第 1 步 → 第 6 步 一张张往下学。 这条主线是「从最小的持久化开始，一层层扩到能撑住界面的数据库」： 第 1 步键值配置 → 第 2 步文件与 IO 设备（所有存储的地基）→ 第 3 步结构化文本 → 第 4 步只读资源（不进磁盘的那些东西）→ 第 5 步关系数据库 → 第 6 步数据库接界面。 本模块有两道硬坎： ① 第 2 步「三种模式混用」坎——文本模式会做换行翻译，于是 pos() 和真实文件偏移不再相等； readAll() 吃大文件；QTextStream::setCodec() 在 Qt6 已经删了，只剩 setEncoding()； ② 第 5、6 步「连接与缓存」坎——一个连接属于创建它的线程，跨线程共用 = 未定义行为； 模型是缓存，你直接改库它不知道；setFilter 会重新查询，未提交的改动和它怎么相处要心里有数。 持久化是全模块里最容易「测试环境都对、用户机器上出事」的一段：路径、权限、编码、磁盘满、并发写， 这些东西你的开发机上一样都不缺，一样都不会发生。 每章重点与练习见 📖 学习指南。

03 · JSON
QJsonValue 只有七个类型枚举（Null/Bool/Double/String/Array/Object/Undefined）；读的那一族 to* 全都没有 bool* 出参，类型不对静静回默认值，想知道「有没有这个键」只有 contains()；QJsonObject 的键是集合不是队列（公开接口没有 keyAt），要下标语义只有 QJsonArray；顶层解析只有两个入口、不给多文档；toJson() 的字节不能当协议去 diff。

05 · Qt SQL 的四件事

06 · 数据库接界面
三个坑是三张脸：模型不是数据库、视图不是模型。QSqlQueryModel 是只读快照（连 setData 都没声明），QSqlTableModel 是可编辑的行集合；OnFieldChange / OnRowChange / OnManualSubmit 三种编辑策略解释「我改了为什么库里没变」；setFilter/setSort 会重新查询（未提交改动会不会丢标 Soft，硬账只记显式提交之后一定不丢）；QSqlRelationalTableModel 让外键显示成汉字。

📚 学习建议

  • 先想「这份数据归谁」再选容器：用户偏好 → QSettings；结构化文档 → 文件 + JSON；只读常量 → qrc；有查询/关联需求 → SQLite。选错了容器，后面每一行都在跟它打架。
  • 一切写盘都假设它会失败：磁盘满、权限不足、文件被另一个进程占着。检查 open() 的返回值、读 errorString()、关键文件用 QSaveFile 原子替换。
  • 编码只有一条路：全链路 UTF-8，读的时候 QString::fromUtf8，不要依赖系统默认编码。QTextStream::setCodec 在 Qt6 里已经不存在了。
  • 数据库先想线程再想 SQL：一个连接一条线程；句柄可以传，连接不能跨线程用；收尾 removeDatabase(名字)，别指望析构。
  • 接界面时记住「模型是缓存」：绕过模型直接改库，界面不会自己知道；要让界面看到，就通过模型改，或者重新查询。
  • 跑之前先想清楚要拿什么证据：本模块每个示例都把「存的类型 / 读的类型 / 实际拿到什么」「改了几行、提交没提交」打印出来。你改自己的代码时也留这套习惯。

👴 老师傅的话

徒弟，存储这一块，是「事后最难改」的一块。界面丑，改一版 qss 就好看；架构乱，重构几周能救；但数据格式定错了、写盘路径选错了、连接线程模型错了，那是在用户机器上、在升级之后、在某个周五晚上才发作的东西。所以这一阶段我不教你把 API 背全，只教你四个问题：归谁、什么形状、怎么写不坏、写坏了怎么知道。

  • 第一条：配置别用自己发明的格式。 QSettings 已经把 ini/注册表的差异吃掉了，你手写一个 config.txt，很快就得自己处理转义、层级、并发写。
  • 第二条：写文件要原子。 直接 QFile 覆盖写，掉电就是半个文件；QSaveFile 先写临时文件再 rename，这是「要么全新、要么全旧」的唯一保证。你的数据越贵，这一条越不能省。
  • 第三条：类型要在写的那一刻定死。 QSettings 的自动转换、QJsonValue::toInt() 的静静回默认值、SQL 里的 NULL——它们都不报错，只是给你一个「看起来能用」的错值。读的时候永远用 contains()、isXxx() 先把形状问清。
  • 第四条：数据库连接的寿命 ≠ 对象的寿命。 QSqlDatabase 是句柄不是连接，拷贝一次不会开第二条连接；连接归属创建它的线程；收尾用 removeDatabase()。这三句，够你避开九成的 SQL 崩溃。
  • 第五条：只读的东西别放磁盘。 图标、qss、翻译、默认配置——放进 qrc 编进 exe。用户改不坏、装到哪儿都能找到、升级不会丢。

这一关啃完，你的程序才真正「有记忆」。而一个能记住东西的程序，才谈得上是产品。加油，徒弟！
