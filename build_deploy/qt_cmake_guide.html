🔧 Qt6 的 CMake 到底怎么写

从 6 行骨架到部署，五份可单独构建的工程逐份拆开

📖 这一页讲什么

这一页是「构建」这件事的地图。左边是 CMakeLists.txt 里的每一行，右边是它到底让构建系统做了什么； 五个目录 qt_cmake_01_widgets … qt_cmake_05_translations 各自是一个独立工程， 每个都能在自己的目录里单独 cmake -B build -S .，不依赖仓库顶层。

先记住一件事：CMake 不编译代码。它只做三件事——读你的描述、生成「Ninja / Makefile / Visual Studio 工程」， 然后由那个生成物去调编译器。所以「CMake 报错」和「编译报错」是两个阶段，别混着查。

诚实标注：本库当前环境无法链接 Qt 运行时，这五份工程未在本机实际 configure/build； 其中的 C++ 源码都过了 moc + g++ -fsyntax-only -std=c++17 -Wall -Wextra 检查（零 error、零 warning）， CMake 里用到的函数与参数都对着本机 C:\msys64\ucrt64\lib\cmake\Qt6* 的真实实现核对过。

① 最小骨架：六行

这是 qt_cmake_01_widgets/CMakeLists.txt 的骨架（注释在文件里有，这里只留骨架）：

cmake_minimum_required(VERSION 3.21)
project(hello_widgets LANGUAGES CXX)
set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
find_package(Qt6 REQUIRED COMPONENTS Widgets)
qt_standard_project_setup()
qt_add_executable(hello_widgets main.cpp)
target_link_libraries(hello_widgets PRIVATE Qt6::Widgets)

每一行在做什么

  • cmake_minimum_required(VERSION 3.21)：低于这个版本的 CMake 会拒绝配置。Qt 6.12 建议 ≥ 3.21；本库所有示例都按这个下限写。
  • project(... LANGUAGES CXX)：声明工程名与语言。只写 CXX，不写 C，能省掉一次 C 编译器的探测。
  • find_package(Qt6 REQUIRED COMPONENTS Widgets)：找 Qt6Config.cmake，并导入 Qt6::Widgets 这个导入目标。它自带 include 路径、编译定义（例如 QT_WIDGETS_LIB）和依赖的 Gui、Core。
  • qt_standard_project_setup()：打开 AUTOMOC 与 AUTOUIC、设置策略组、定输出目录、准备 i18n 变量。它不打开 AUTORCC。
  • qt_add_executable(...)：在 add_executable 之上做 Qt 特化的事（Windows 入口点、移动平台处理、标记为 Qt 目标）。
  • target_link_libraries(... PRIVATE Qt6::Widgets)：可执行文件没有下游，PRIVATE 足够；库就不一样了（见第 ③ 节）。
常见误解：qt_standard_project_setup() 并不等于「打开所有自动化」。在 6.12 的实现里， 它只对 CMAKE_AUTOMOC 和 CMAKE_AUTOUIC 赋 TRUE； CMAKE_AUTORCC 保持原样。想用「.qrc 当源文件」的老路线，必须自己打开它（第 ④ 节有两个工程的原始写法）。

② 为什么不是我 include 了 Qt 头就能编？

因为编译器需要头文件路径，链接器需要库文件名，而这两样都不是「头文件放在那儿」就能自动知道的。 Qt6::Widgets 这个导入目标把三样东西一起交给你：

它带的东西内容（举例）不链接它会怎样
INTERFACE_INCLUDE_DIRECTORIES…/include/qt6、…/include/qt6/QtWidgets 等fatal error: QApplication: No such file or directory
INTERFACE_COMPILE_DEFINITIONSQT_WIDGETS_LIB、QT_CORE_LIB 等某些头文件里被 #ifdef 包住的声明消失（例如 QtTest 里操作 QWidget 的那组重载）
INTERFACE_LINK_LIBRARIESQt6Widgets.dll / libQt6Widgets.so 及其依赖链接期 undefined reference to QApplication::…

find_package(Qt6 COMPONENTS Widgets) 会自动把 Gui、Core 带进来——因为 Widgets 依赖它们。 所以你不需要写三遍 find_package。

③ 一个库 + 一个界面：PUBLIC / PRIVATE 到底影响谁

看 qt_cmake_02_structure：

add_library(greeting STATIC
    src/greeting.cpp
    include/greeting/greeting.h          # 头文件放进源列表：让 AUTOMOC 与 IDE 都看得到
)
target_include_directories(greeting PUBLIC ${CMAKE_CURRENT_SOURCE_DIR}/include)
target_link_libraries(greeting PUBLIC Qt6::Core)

add_executable(greeting_app src/main.cpp)
target_link_libraries(greeting_app PRIVATE greeting Qt6::Widgets)
  • PUBLIC：我自己用，下游也继承。所以 greeting_app 不用再写 include 路径，也能 #include <greeting/greeting.h>，还能 include <QTimer>（因为 Qt6::Core 是 PUBLIC 传下来的）。
  • PRIVATE：只我自己用，下游看不到。Qt6::Widgets 在 app 上是 PRIVATE——这很好，说明「界面」是这一层的事，库本身不知道界面存在。
  • INTERFACE：我自己不用、只给下游用（本工程没用到，常见于 header-only 库）。

这正是第拾阶段第 3 讲分层的构建层面：依赖方向写在 CMake 里，比写在文档里管用。 库的 PUBLIC 属性里一旦出现 Widgets，下游就再也没法把它链进命令行工具。

④ 资源：两条路线，都要会认

qt_cmake_03_resources 同时用了两条路线：

# 路线 B（推荐）：直接从文件列表造资源，不需要 .qrc
qt_add_resources(resource_app "app_assets"
    PREFIX "/"
    FILES assets/style.qss assets/logo.svg
)                          # → ":/style.qss"、":/logo.svg"

# 路线 A（传统）：.qrc 当源文件，靠 AUTORCC 跑 rcc
set(CMAKE_AUTORCC ON)      # ← qt_standard_project_setup() 不会替你打开它
target_sources(resource_app PRIVATE assets/legacy.qrc)   # → ":/legacy/style.qss"

两条路的产物都进同一棵资源树，运行时读法完全一样：QFile(":/…")。 区别在构建期：qt_add_resources 由 Qt 的 CMake 层管理（增量、别名、压缩都能配）， .qrc 则由 rcc 处理。Qt6 的 CMake 层默认让 AUTORCC 用 zstd 压缩， 本机 Qt 没编 zstd 或你设了 QT_NO_AUTORCC_ZSTD 时会追加 --no-zstd。

资源是只读的。要写用户数据，请用 QStandardPaths::writableLocation() 拿目录， 别试图写 :/。运行时细节见storage/04_resource_system.cpp 与 图解 · 资源系统。

⑤ 测试：让 CTest 替你判卷

find_package(Qt6 REQUIRED COMPONENTS Core Test)
enable_testing()                                   # 必须在顶层目录调用

add_library(calc STATIC src/calc.cpp include/calc/calc.h)
target_link_libraries(calc PUBLIC Qt6::Core)

add_executable(tst_calc tests/tst_calc.cpp)
target_link_libraries(tst_calc PRIVATE calc Qt6::Test)
add_test(NAME tst_calc COMMAND tst_calc)
set_tests_properties(tst_calc PROPERTIES
    ENVIRONMENT "QT_QPA_PLATFORM=offscreen" TIMEOUT 30)

add_test 只做一件事：把「跑这个可执行文件」注册成用例，退出码 0 = 通过。 QtTest 的 QTEST_GUILESS_MAIN 不需要平台插件（它只建 QCoreApplication）； 但把它设成 offscreen 是个好习惯——哪天你换成 QTEST_MAIN，CI 上没有显示器也不会突然红。

./build/tst_calc 单独跑时，每个测试函数会打印一行 PASS 或 FAIL； ctest --test-dir build --output-on-failure 则把它们收成一张表。测试类怎么写见 quality/01_qtest_unit.cpp。

⑥ 翻译：lupdate → lrelease → 资源

find_package(Qt6 REQUIRED COMPONENTS Widgets)
find_package(Qt6 QUIET COMPONENTS LinguistTools)    # 精简安装可能没带

qt_standard_project_setup(
    I18N_SOURCE_LANGUAGE zh_CN
    I18N_TRANSLATED_LANGUAGES en
)

qt_add_executable(translations_app src/main.cpp)

if(Qt6LinguistTools_FOUND)
    qt_add_translations(translations_app TS_FILE_BASE translations_app)
endif()
阶段工具产物谁触发
抽取字符串lupdatetranslations_app_en.ts构建时的 update_translations 目标
编译翻译lreleasetranslations_app_en.qmrelease_translations / 构建
装进程序Qt 的 CMake 层:/i18n/translations_app_en.qmRESOURCE_PREFIX 默认 /i18n
运行期生效QTranslator—你的代码：load() + installTranslator()
第一次构建生成的 .ts 是空的（原文都在，译文是空的）。要用 Qt Linguist 打开它、逐条填译文， 再重新构建。.ts 是 XML、适合进版本库；.qm 是二进制，通常不提交。

⑦ 从 build 目录到别人的电脑

开发机上能跑，是因为 Qt 的 DLL 在 PATH 里（或者你在 Qt Creator 里运行，它替你设好了环境）。 拷到别人电脑上就只剩一个 exe 和一句 0xC0000135。标准做法： 

# Windows：让 Qt 自己读 exe 的导入表，把需要的 DLL 与插件拷到 deploy/
windeployqt --release --dir deploy build/hello_widgets.exe

# deploy/ 里至少要有：
#   hello_widgets.exe
#   Qt6Core.dll Qt6Gui.dll Qt6Widgets.dll …
#   platforms/qwindows.dll        ← 缺它 → "no Qt platform plugin could be initialized"
#   styles/ imageformats/         ← 缺它 → 控件样式或图片悄悄不见

install(TARGETS … RUNTIME DESTINATION bin) 那条规则是给「正规安装」用的： cmake --install build --prefix dist 把产物放到 dist/bin，再用 windeployqt 收依赖。 完整的目录树、报错对照与 qt.conf 用法见 图解 · 部署。

静态链接能让「一个 exe 走天下」，代价是：每个插件都要 Q_IMPORT_PLUGIN 显式引入、 体积大、而且 LGPL 下静态链接有额外义务。团队项目里更常见的是「动态链接 + 安装包」。
