🔧 第拾壹阶段 · 构建与部署

五份可以单独 configure 的工程 · 从 6 行 CMake 骨架走到别人的电脑里

📖 模块简介

这一阶段跟前面十个都不一样：前面讲的是「代码怎么写」，这里讲的是「代码怎么变成一个能交给别人的东西」。 你会发现很多「在我这儿能跑」的问题，根子既不在 C++ 也不在 Qt 的 API，而在构建与部署这一层： 头文件路径没传下去、moc 没跑、资源没进 exe、DLL 没带、插件目录缺一层。

本阶段有 5 个独立工程，每个目录都有自己的 CMakeLists.txt 和 project()， 必须进到各自目录里单独 configure（顶层只检查它们存在，不会 add_subdirectory 进来）：

  • qt_cmake_01_widgets —— 最小骨架：四行必需 + 两条产物规则
  • qt_cmake_02_structure —— 一个库 + 一个界面：PUBLIC/PRIVATE、include 目录、手写 AUTOMOC
  • qt_cmake_03_resources —— 资源的两条路线：qt_add_resources（带 / 不带 BASE，路径不一样）与 .qrc + AUTORCC
  • qt_cmake_04_tests —— 库 + 应用 + QtTest + CTest，一条命令判卷
  • qt_cmake_05_translations —— tr() → .ts → .qm → :/i18n/

配套讲义是 qt_cmake_guide.html：那一页把 CMake 的每一行拆开讲，并给出报错对照表与 windeployqt / qt.conf 的用法。部署的可视化复盘见 图解 · 部署。

环境事实：Qt 6.12.0、MinGW-w64 GCC 13.1.0（Qt 官方安装器自带：D:\Qt\Tools\mingw1310_64）、CMake ≥ 3.21（本机 3.30.5）+ 生成器 MinGW Makefiles、C++17。 本阶段所有 CMake 用法都对着本机 D:\Qt\6.12.0\mingw_64\lib\cmake\Qt6* 的真实实现核对过—— 包括一条容易被抄错的：qt_standard_project_setup() 只打开 AUTOMOC 与 AUTOUIC，不打开 AUTORCC。

实测口径：五份工程都在本机各自 configure / build / run 过一遍（Qt 6.12.0 + MinGW 13.1.0 + CMake 3.30.5 + MinGW Makefiles）。 五次构建的 warning: / error: 行数都是 0；四个 GUI 目标在 -platform offscreen 下退出码全 0； 第 4 份的 CTest 1/1 Passed（tst_calc.exe 自报 10 passed, 0 failed, 0 skipped）。 每个工程都在文件头注明「怎么构建、跑起来看到什么」。

⚠ 第 5 份（翻译）原先是坏的，而且坏得很难看：qt_add_translations 首次 configure 生成的 .ts 是空的， 空 .ts 过 lrelease 得到一个 30 字节、0 条译文的 .qm，而 QTranslator::load() 对它照样返回 true —— 于是程序在界面三行全是中文的同时打印「翻译是否生效： true」。 它量的从来不是「翻译生效」，只是「这个文件是不是合法 .qm」。现在换成带基线对照的 11 项台账，不符就参与退出码； 仓库里提交的 translations_app_en.ts 已填好译文，直接 cmake --build build 就能看到英文；等你往 main.cpp 里加了新的 tr()， 才需要先跑 cmake --build build --target update_translations 把源串抽进 .ts —— 它会合并、不会冲掉你填好的译文（本机重跑对过前后两份文件）， 但会用「同文启发式」把别的上下文的译文抄给新上下文，那就是台账的账8。全过程写在 qt_cmake_05_translations/src/main.cpp 的文件头。

📂 五个工程

5 个目录 = 5 个独立工程，按 01 → 05 顺序做，每个都先 cmake -G "MinGW Makefiles" -B build -S . 再 cmake --build build。 这条主线是「先建起来 → 再拆成层 → 再把它需要的文件带进去 → 再让它能自证 → 最后让它能说别的语言」： 01 最小骨架 → 02 库与界面 → 03 资源 → 04 测试 → 05 翻译，之后接讲义第 ⑦ 节的部署。 本阶段有两道硬坎： ①「Qt6 找不到」坎——不是 Qt 没装，而是 CMake 不知道它在哪：-DCMAKE_PREFIX_PATH=… 或改用 qt-cmake； ②「undefined reference to vtable」坎——有 Q_OBJECT 却没跑 moc。AUTOMOC 对头文件自动生效； 类写在 .cpp 里时，必须在文件末尾 #include "xxx.moc"（第 05 个工程就用了这一手）。 每章重点与练习见 📖 学习指南。

总纲

📚 学习建议

  • 一个工程一个构建目录：每个子目录单独 cmake -B build -S .。共享构建目录会让你在两份 CMakeLists 之间反复踩缓存。
  • 先 configure，再 build，再 run：三个阶段的报错含义完全不同。configure 挂是「找不到 Qt / 写错语法」，build 挂是「编译或 moc」，run 挂是「DLL / 插件 / 资源」。
  • 用 qt-cmake 或 -DCMAKE_PREFIX_PATH：这是「Qt6 找不到」的唯一正解。别把 Qt 的 bin 加到 PATH 就以为解决了。
  • 看见 vtable 未定义，先想 moc：检查 AUTOMOC 是否对该目标生效；类写在 .cpp 里，就 include 生成的 .moc。
  • 部署是最后一步，但要从一开始就想着它：产物集中在 build/bin、安装规则写清、资源走 qrc、依赖用导入目标，这些习惯都会让 windeployqt 那一步简单很多。
  • 「能 build」不等于「能验证」：五份工程本机都 build 通、跑通了（退出码全 0，第 4 份 CTest 1/1）。但第 5 份用 load() 的返回值当「翻译生效」的证据，build 得再干净也还是在打印假话。判据要选那个真能区分对错的量——这里叫 isEmpty()，或者干脆拿译文和源文比一次。

👴 老师傅的话

徒弟，构建这一层最不受待见——写业务的人嫌它琐碎，可一旦它出问题，整条流水线都停。师傅见过太多人「代码写得漂亮，但交不出去」。所以这一阶段只教你一件事：把「在我这儿能跑」变成「在别人那儿也能跑」。

  • 第一条：构建文件也是代码，要读要写要改。 从网上抄一段 CMakeLists 而不理解它，等于在黑箱上盖房子。这一阶段的六行骨架，你要能默写。
  • 第二条：依赖方向写在构建文件里。 库的 PUBLIC 里出现 Widgets，下游就再也进不了命令行；反过来，把边界守住，代码想乱都难。
  • 第三条：moc 不是魔法，是一个构建步骤。 看见 vtable 未定义，就知道是 moc 没跑或没被链接；看见「写在 .cpp 里就编不过」，就知道要 include xxx.moc。
  • 第四条：部署不是拷 exe。 平台插件、样式插件、图片格式插件、运行时 DLL、qt.conf，一个都不能少。第 ⑦ 节那张目录树，你要能凭记忆画出来。
  • 第五条：版本要对齐。 Debug 的 Qt DLL 不能配 Release 的 exe，6.12 的头文件不要配 6.5 的库。所有「莫名其妙」的崩溃，先怀疑这个。
