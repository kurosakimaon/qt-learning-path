⚠️ 先读这一段：这份资料的边界

写作环境是 Qt 6.12.0 + Windows + MinGW-w64 GCC 13.1.0（Qt 官方安装器自带：D:\Qt\Tools\mingw1310_64）+ CMake ≥ 3.21（本机 3.30.5）+ 生成器 MinGW Makefiles + C++17。 这一套不是「写完没跑」：73 个示例全部 moc + 编译（0 error / 0 warning）、全部链接成功、全部无头跑完， ctest --test-dir build 本机那一轮 75/75 全过（含实战项目的单元测试）； build_deploy/ 的 5 个工程与 projects/todo_desktop 也各自真实构建并运行过。 每个示例自己打的证据行都存进仓库：runlogs/<target>.log（UTF-8，75 份）， runlogs/summary.txt 只记失败与超时——全过那一轮它是空的，别当成「没跑」。

每个类、函数、枚举值、重载都对着本机 D:\Qt\6.12.0\mingw_64\include（声明）与 D:\Qt\6.12.0\Src\qtbase\src（实现）逐字核对过，注释里标着头文件名与行号； 核对不上的一律不写——这比写错一个 API 更值。 两条边界要留个心：① 行号只对得住本机这一份 6.12.0，换个小版本 qobject.cpp 就整体漂移， 按行号找不到时改用函数名搜；② 凡是只写「预期」而没有「本机实测」字样的数字，都是会随版本 / 驱动 / 字体 / 磁盘变的那一类 （定时器精度、字体度量、execBatch 的驱动支持）。跑出不一样的结果， 以你打印出来的为准，并以那份差异为准回来修订注释：证据优先于权威。

事件系统 · Events events/ 进阶
⏱️ 建议 1.5 周 · 7 个示例 · 2 张图解

Qt 程序不是「从 main 走到 return」，而是「走进 exec() 就再不回来」。 重绘、按钮响应、定时器、拖放，全是这台机器转出来的。这一阶段把事件循环、三层派发、过滤器、定时器、 输入与焦点、自定义事件、拖放逐个钉死，并且全程不用鼠标键盘——自己构造事件投进去，用顺序和次数当证据。

  • 画出 notify → event() → handler 三层链，说清 sendEvent 与 postEvent 的时序差
  • 用 eventFilter 不继承就改行为；知道吞掉 press/release 后 clicked() 为什么是 0
  • QTimer 三档精度 + QElapsedTimer 实测间隔；知道「没有事件循环，定时器一次不响」
  • 读懂 Qt6 输入 API：position() 是 QPointF、button() vs buttons()、angleDelta() vs pixelDelta()
  • 写对一个拖放：QMimeData + acceptProposedAction() + startDragDistance()
本阶段硬坎：事件 ≠ 信号。 事件是系统层语义（谁来、按了什么），信号是应用层语义（意味着什么）。 QAbstractButton 把 QMouseEvent 翻译成 clicked()；而 btn->click() 直接发信号、绕过事件——这就是为什么过滤器拦不住它。

肆
元对象系统 · Meta-Object metaobject/ 进阶
⏱️ 建议 2 周 · 8 个示例 · 3 张图解

Qt 与别家 GUI 库的根本区别都在这一层：Q_OBJECT、moc、连接语义、生命周期、属性、反射。 它在编号上排在控件与事件之后，不是因为它次要，而是因为你得先写过 connect，才看得懂它在替你做什么。 八讲从「会用信号槽」一路读到「读懂元对象表」。

  • 说清 emit 展开成什么、moc 生成哪些函数、连接在什么时候把指针换成分发表下标
  • 会挑连接类型（Auto / Direct / Queued / BlockingQueued / Unique），知道同线程 BlockingQueued 直接死锁
  • 会用 Q_PROPERTY + Q_ENUM + QMetaObject::invokeMethod 做动态调用
  • 能解释对象树所有权、deleteLater 的时机、QPointer 怎么自保
  • 知道 Q_OBJECT 只声明不实现，所以 .cpp 里的类要 #include "本文件名.moc"
本阶段硬坎：moc 的世界只在运行期报错。 属性名拼错、枚举漏写 Q_ENUM、 indexOfMethod 返回 -1 还拿去用——编译器一个字都不说。所以这一阶段的示例刻意把「失败长什么样」打出来。

⏱️ 建议 2 周 · 8 个示例 · 2 张图解

柒
并发与线程 · Threads threads/ 中高级
⏱️ 建议 2 周 · 8 个示例 · 1 张图解

一条铁律先记住：只有 run() 跑在新线程里，别的都在原线程。 从亲和性讲到跨线程信号，再到四种同步工具、QtConcurrent、QRunnable + 线程池、取消与收尾， 最后用本地套接字做一次进程间通信。全程一次 terminate() 都不调——那是拆房子，不是收摊。

  • 说清对象亲和性与「槽在哪个线程跑」，会用 moveToThread 的正路
  • 跨线程只用排队信号（参数被拷贝），共享数据用 mutex / atomic / 只读
  • QtConcurrent、QThreadPool、QRunnable 三种并行写法各用在什么场合
  • 会写不靠 terminate() 的收尾：取消标志 + wait() + deleteLater
本阶段硬坎：线程归属。 在错误的线程里创建 QObject、在 run() 里碰界面、 用 Direct 连接跨线程——这三件事都「能编过、有时也能跑」，然后在你演示那天崩。

🧘 老师傅的学习心法

七条铁律

  • 先跑，再改，最后才想。 每个示例先原样跑通、看清它吐的证据，再改一行、看证据怎么变。光读代码，你记住的是「别人写对了」，不是「我为什么错」。
  • 证据优先于记忆。 顺序、次数、耗时都要亲自打印出来。这份资料里所有注释都标了头文件行号，就是让你随时能去核对——包括核对师傅。
  • 每阶段撞一次坎。 第叁阶段故意吞掉事件看信号变 0；第陆阶段故意不 mapToSource 看空值；第柒阶段故意在错线程碰界面。改错一次再改回来，比看十遍正确代码管用。
  • 别跳第肆和第陆。 前者是 Qt 与普通 C++ 的分界线，后者是「会摆界面」与「会做数据界面」的分界线。这两段跳过去，面试第一轮就会露底。
  • 只信能复现的现象。 同事说「Qt 有 bug」，你先写十行把它复现出来；复现不出来，八成是用法问题，剩下两成才是真 bug——而真 bug 也需要复现才能报。
  • 每讲收一个「可复用件」。 自绘控件、自定义模型、委托、线程收尾模板、带超时的请求封装——这些是你以后真正会抄自己的地方。
  • 写给人看，跑给机器看。 注释解释「为什么」，代码保证「编得过、跑得完、测得着」。风格争论可以先放一放，先让 ctest 全绿。
🚀 怎么开始

三步上手

  1. 先验证这份资料本身。 不装 Qt 也能跑：这个脚本只做 moc 与语法检查，不链接、不运行， 用来确认「73 个示例在这个编译器上都能编过」。 
    # 需要 MSYS2 ucrt64 的 g++ 与 moc（脚本里的 MSYS 变量可改）
$ bash _tools/check_syntax.sh
#   OK   start/01_hello_window.cpp
#   ...
# 校验完成：通过 74，失败 0

# 只查一阶段 / 只查一个文件
$ bash _tools/check_syntax.sh events
$ bash _tools/check_syntax.sh events/01_event_loop.cpp
  2. 在装了 Qt 的机器上配置工程。 Qt 6.12 的路径按你自己的安装改；MSYS2 用户直接写 D:/Qt/6.12.0/mingw_64。 
    # 配置（找不到 Qt 时不会失败，只会打印一段「你该装什么」）
$ cmake -G "MinGW Makefiles" -B build -S . -DCMAKE_PREFIX_PATH=D:/Qt/6.12.0/mingw_64

# 只编一个示例，先确认工具链通了
$ cmake --build build --target start_01_hello_window
$ ctest --test-dir build -R start_01 --output-on-failure
  3. 再全量跑。 73 个示例同时是 CTest 用例，一律以 QT_QPA_PLATFORM=offscreen 无头运行、120 秒超时； 每个示例跑完自己 quit()，不需要你点任何按钮。 
    $ cmake --build build --target all_demos
$ ctest --test-dir build --output-on-failure

# 想看某个示例的真实输出（证据都在终端里）
$ QT_QPA_PLATFORM=offscreen ./build/bin/events_02_event_dispatch

环境要求：Qt 6.x（本库按 6.12 编写）、CMake ≥ 3.21、支持 C++17 的编译器（MinGW / MSVC / Clang 均可）、Ninja 可选。 Windows 上产物集中在 build/bin，方便 windeployqt 一次收齐依赖。 没有显示器、没有鼠标键盘都能跑——这是整套资料的默认运行方式。

👴 老师傅的话

徒弟，Qt 这门手艺，最容易被误解的是「它只是个画界面的库」。真上手你会发现：它给你的是一整套 对象怎么活、消息怎么走、数据怎么流 的规矩。你把这套规矩摸顺了，写出来的程序就稳； 摸不顺，就会一直在「偶尔崩一下」「偶尔卡一下」里打转，而这些「偶尔」全都有名字，就在这十一个阶段里。

  • 别急着做漂亮界面。 前三个阶段能把窗口摆出来、把按钮点响，人容易飘。真正的分水岭在第肆与第陆：一个讲清 Qt 凭什么不同于普通 C++，一个讲清数据凭什么不塞进控件里。
  • 事件是系统说话，信号是程序说话。 分不清这两层，你会一直在「为什么我的过滤器拦不住按钮」和「为什么 btn->click() 不算点击」之间打转。
  • 线程只信一条。 只有 run() 跑在新线程里；界面只在主线程碰；跨线程只走排队信号。剩下所有花招，都是在给这条铁律打补丁。
  • 性能不是调出来的，是量出来的。 第陆和第拾会各给你一次「十万行」的账：该省的地方省在「只问可见区」，不该省的地方省在「别每格都重新量尺寸」。
  • 能交付才算学会。 第拾壹阶段那五个小工程，看着最不像「知识点」，却是最像上班的：别人拿到你的目录，三条命令能编、拷到别的电脑能跑，这才叫完成。

最后一句：这份资料里所有「预期输出」都是推理，不是实测。等你在能链接的机器上跑出真实数字， 以你打印出来的为准——把自己当工程师，而不是当读者。慢慢来，十一个阶段，一个都别跳。
